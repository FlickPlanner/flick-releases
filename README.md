# Flick Planner Sparkle Releases

This repository publishes Flick Planner's Sparkle appcast and current notarized DMG through GitHub Pages:

- Appcast: `https://flickplanner.github.io/flick-releases/updates/appcast.xml`
- Updates: `https://flickplanner.github.io/flick-releases/updates/`

The appcast must be generated by Sparkle's tooling. Do not edit a generated appcast, its release notes, or any
signature by hand.

## One-time migration to the release Mac

### Transfer the existing Developer ID identity

Sparkle trusts Flick updates through both its EdDSA key and the Apple signing identity used by the installed app.

On the old release Mac:

1. Open Keychain Access and select the login keychain's **My Certificates** category.
2. Expand `Developer ID Application: Raphael Kitahara (97247339Z3)` and confirm that a private key is nested below it.
3. Select the identity and its private key, then use **File → Export Items**.
4. Export a password-protected `.p12` and transfer it through an encrypted or otherwise trusted channel.

On the new release Mac:

1. Import the `.p12` into the login keychain and remove every temporary transfer copy.
2. Verify the identity:

   ```sh
   security find-identity -v -p codesigning
   ```

3. Sign in to the same Apple Developer account in Xcode so automatic signing can fetch the direct-distribution
   provisioning profile.

Do not revoke this Developer ID certificate before confirming that the next Sparkle update installs successfully.

### Back up the Sparkle key

The recovered private key is stored in the new Mac's login Keychain under Sparkle account `flick-planner`. It matches
the public key already embedded in released Flick builds:

```text
s1b0IgN/Waq8406HjjSPLhL1pEg4SvJEsfmqjflVLs8=
```

Before releasing, export the private key using the same Sparkle 2.9.4 tools resolved by Flick:

```sh
SPARKLE_BIN="../flick-app/Tuist/.build/artifacts/sparkle/Sparkle/bin"
"$SPARKLE_BIN/generate_keys" --account flick-planner -p
"$SPARKLE_BIN/generate_keys" --account flick-planner -x /secure/offline/location/flick-sparkle-key
```

The exported file is an unencrypted signing secret. Move it immediately into an encrypted password manager or
offline encrypted backup, remove the plaintext transfer copy, and test restoring it on a separate Keychain before
publishing. Never commit it or pass it as a command-line argument.

### Configure notarization

Create a Keychain profile on the release Mac. The command prompts for the Apple ID, team ID `97247339Z3`, and an
app-specific password instead of saving them in a script:

```sh
xcrun notarytool store-credentials flick-notary
```

The release scripts and repository must never contain Apple credentials, app-specific passwords, `.p12` files, or
Sparkle private keys.

## Build, package, and notarize

1. In Xcode, archive the `FlickNotarized` scheme and export it using **Developer ID** distribution. Confirm the
   exported app reports marketing version `2.1.2`, build `3` for the recovery release, bundle ID `com.pawtask`, and
   team ID `97247339Z3`.
2. Copy the exported app to a clean staging directory. Remove Finder/resource metadata from the staging copy before
   building the image:

   ```sh
   xattr -cr /path/to/staging/Flick.app
   codesign --verify --deep --strict --verbose=4 /path/to/staging/Flick.app
   ```

3. Build a DMG containing only `Flick.app`, presentation assets, and an `/Applications` symlink. Do not re-sign nested
   Sparkle helpers manually when using Xcode's Developer ID export.
4. Sign and notarize the final disk image:

   ```sh
   codesign --force --sign "Developer ID Application: Raphael Kitahara (97247339Z3)" \
     --timestamp /path/to/Flick-2.1.2.dmg
   xcrun notarytool submit /path/to/Flick-2.1.2.dmg \
     --keychain-profile flick-notary --wait
   xcrun stapler staple /path/to/Flick-2.1.2.dmg
   xcrun stapler validate /path/to/Flick-2.1.2.dmg
   spctl --assess --type open --context context:primary-signature \
     --verbose=4 /path/to/Flick-2.1.2.dmg
   ```

## Generate the signed appcast

Run the preparation command only after the final DMG passes notarization:

```sh
Script/prepare_update.sh --dmg /path/to/Flick-2.1.2.dmg
```

Flick allows automatic updates and enables them by default. The recovery appcast still marks build `3` as the
minimum automatic-update version, requiring older builds to obtain user approval for this recovery update. Later
updates from build `3` can use Sparkle's automatic path.

The command:

- validates the DMG, app, Developer ID team, notarization tickets, Sparkle settings, and sandbox entitlements;
- verifies that the embedded public key matches Keychain account `flick-planner`;
- generates archive and feed EdDSA signatures with Sparkle 2.9.4;
- sets recovery build `3` as the minimum automatic-update version;
- validates the generated versions, signatures, lengths, MIME type, and artifact references;
- moves the previously published DMG into ignored `old_updates/`; and
- installs the new DMG and signed appcast under `updates/`.

Review the resulting Git diff before committing. Keep only the current DMG in the published tree. Old artifacts remain
recoverable from Git history and from the local ignored archive.

## Publish and verify

Push the reviewed release commit to `main` and wait for GitHub Pages' `pages-build-deployment` workflow to finish.
Then verify the deployed feed and downloads:

```sh
Script/verify_live_update.sh
```

The local preparation command cryptographically verifies the feed and archive signatures. The validation workflow
also rejects structurally unsigned or malformed feeds, duplicate/non-increasing build numbers, missing local
artifacts, and declared byte lengths that differ from the committed DMG.

GitHub Pages has a recommended 1 GB source/site limit and a soft 100 GB monthly bandwidth limit. This repository
already contains 319.22 MiB of packed history as of this runbook's creation, so monitor it with
`git count-objects -vH`. If growth or bandwidth approaches those limits, move DMGs to GitHub Release assets while
leaving the small appcast on Pages.

## Recovery release acceptance

Before publishing build `3`, create a Developer ID-signed old-version test host containing the production Sparkle
public key and a staging feed URL. Confirm:

1. The scheduled check shows Flick's sidebar Update button without presenting an unsolicited Sparkle window.
2. Clicking Update opens Sparkle's standard interface and installs the recovery DMG.
3. The app relaunches as build `3`, and a subsequent update check reports no update.
4. A later build signed with the same `flick-planner` key updates normally.
